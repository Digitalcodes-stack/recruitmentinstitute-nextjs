1.2 Design pattern
--------------------------------------------------------------------------------
Mirrors the existing app/integrations/meetings/{factory,provider}.py pattern
already used in the codebase — an ABC interface (AIProvider) with one
concrete class per backend, selected at runtime by a factory function reading
AI_PROVIDER from settings. No endpoint or service code references a specific
provider class directly; everything depends on the abstract interface.

AIProvider interface (app/services/ai/base.py):
  async def analyze_performance(score, percentage, topic_scores) -> PerformanceAnalysis
  async def generate_notes(topic_name) -> str
  async def generate_study_plan(weak_topics, strong_topics) -> dict
  async def generate_recommendations(percentage) -> list[str]

1.4 API contract (prefix /api/v1/assessment, all behind Bearer JWT)
--------------------------------------------------------------------------------
POST /submit
  Body: { assessment_id, topic_scores: [{topic_name, correct, total}] }
  Flow: validate assessment exists -> compute score/percentage -> persist
        StudentAssessment -> call provider.analyze_performance() ->
        persist AIAssessmentAnalysis -> for each weak topic, fetch-or-
        generate cached notes (Redis, 7-day TTL) -> persist AIGeneratedNote
        rows -> call provider.generate_study_plan() -> persist
        StudentStudyPlan -> call provider.generate_recommendations() ->
        commit everything atomically -> return full result.
  Returns 201 with student_assessment_id, analysis, notes, study_plan,
  recommendations.

GET /result/{id}        -> student_assessment + analysis
GET /notes/{id}         -> list of AI-generated notes for that attempt
GET /study-plan/{id}    -> the generated study plan

PART 2 — BUG FOUND, ROOT-CAUSED, AND FIXED TODAY
================================================================================

2.1 Symptom
--------------------------------------------------------------------------------
Live-tested POST /api/v1/assessment/submit with no real CLAUDE_API_KEY
configured. Got the expected 500 (Anthropic SDK's auth validation:
TypeError "Could not resolve authentication method..."). But the
student_assessments row that had already been written before the AI call
failed was found STILL COMMITTED afterward — an orphaned "completed"
assessment row with no analysis, no notes, no study plan. This breaks the
intended all-or-nothing semantics of submit().

2.2 User decision
--------------------------------------------------------------------------------
User explicitly chose: "Wrap the whole submit() in a DB transaction /
rollback on AI failure" over alternative approaches (e.g. marking the row
as failed/partial instead of preventing the insert).

2.3 Fix implemented
--------------------------------------------------------------------------------
- app/repositories/assessment_repository.py: every write method
  (add_student_assessment, add_analysis, add_notes, add_study_plan) changed
  from individually calling db.commit() to calling db.flush() only. Added a
  single new commit() method.
- app/services/assessment_service.py: submit() now calls
  self.repo.commit() exactly once, at the very end, only after
  generate_recommendations() has succeeded — then refreshes all returned
  ORM objects from the DB.
- Effect: if any step (DB lookup, any of the 4 AI provider calls) raises,
  nothing written via flush() during that request is ever committed;
  Postgres rolls back the whole transaction when the session closes on
  exception.

2.4 Investigation: a confusing false alarm, then the real fix verified
--------------------------------------------------------------------------------
After implementing the fix, a live retest via curl against
http://localhost:8000 still showed an orphaned row — appearing to prove the
fix didn't work, despite an isolated standalone reproduction of the exact
SQLAlchemy flush+exception pattern showing correct rollback (0 rows).

Root-caused today by elimination, in order:
  1. Confirmed the DI dependency chain itself (get_db_session wrapping
     get_db(), which wraps `async with async_session_factory() as session`)
     rolls back correctly in isolation — both as a raw two-layer generator
     test and via AsyncSession.__aexit__ internals (calls close(), which
     calls SessionTransaction.close(), which rolls back if uncommitted).
  2. Confirmed Postgres itself saw a real ROLLBACK statement
     (pg_stat_activity showed `query: ROLLBACK; state: idle` on the
     relevant backend).
  3. Called AssessmentService.submit() directly (bypassing FastAPI's HTTP
     layer entirely) against the real DB and the real failing Claude
     provider call -> 0 rows survived. Service/repository logic confirmed
     100% correct.
  4. Called the real FastAPI app in-process via httpx's ASGITransport
     (exercises the full Starlette/FastAPI routing + AsyncExitStack +
     exception-handler stack, without going through uvicorn/the network
     stack) -> 0 rows survived. Full HTTP-equivalent stack confirmed
     correct.
  5. Conclusion: the orphaned row in the earlier retest came from a STALE
     uvicorn process still bound to port 8000, started before the
     repository/service refactor was made, and invisible to this session's
     process-inspection tools (ps / wmic / Get-Process all returned
     nothing for the PID netstat reported as LISTENING — indicating a
     process from an earlier, now-detached shell context rather than a
     code defect).
  6. Started a fresh uvicorn process on a new port (8010), repeated the
     full live test with a real Next.js-issued JWT (student "Rahul Verma",
     id=11) -> real 500 from the missing Claude API key -> 0 rows in
     student_assessments afterward. Bug confirmed fixed.
