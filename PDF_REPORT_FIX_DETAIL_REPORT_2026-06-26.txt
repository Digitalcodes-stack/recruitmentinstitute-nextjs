2. BUG A — LayoutError: "too large on page" (CRASH)
================================================================================
SYMPTOM
  Generating a report for student_assessment_id=20 (8 weak topics, each with
  long AI-generated notes) crashed with:
    reportlab.platypus.doctemplate.LayoutError: Flowable ... too large on
    page 3 in frame 'normal' ... tallest cell 763.0 points

ROOT CAUSE
  _markdown_to_reportlab() joined EVERY line of the source markdown —
  including blank paragraph-separator lines — with "<br/>". Each blank line
  became a full extra line of vertical space in the rendered PDF. For one
  note this inflated a single Paragraph's rendered height to ~742-763pt,
  almost the entire ~750pt page frame height, leaving no room to fit on any
  single page (Table flowables cannot split a single oversized row).

  Initial (incorrect) theory: removing KeepTogether wrapping around the note
  table would fix it. Tested by removing it — crash persisted, disproving
  the theory. Real cause found by directly measuring Paragraph.wrap() height
  before and after fixes.

FIX
  Rewrote _markdown_to_reportlab() to filter out empty lines BEFORE joining
  with "<br/>", so blank markdown separators collapse instead of each
  producing a full blank rendered line. Height dropped from ~742pt to ~560pt
  per note body — comfortably within page bounds.

  Also restructured note card rendering from nested single-cell Tables
  (Table[[Table[[Paragraph]]]]) into a clean 2-row Table with bare
  Paragraphs as cells, so reportlab's default splitByRow can break a note
  across pages if needed instead of demanding it fit as one atomic block.

VERIFICATION
  Regenerated the same previously-crashing report (student_assessment_id=20)
  — succeeded, status "ready", 10 clean pages confirmed via PyMuPDF page
  count and rendered PNG inspection.

3. BUG B — AI Notes "Key Points" / "Key Terms" extracting garbage
================================================================================
SYMPTOM
  Notes showed garbage fragments instead of real content, e.g.:
    "Improvement\n\nModule", "Topics", "Current Recruitment Processes\nTopics"

ROOT CAUSE
  This was a regression from an EARLIER session's fix (extract_semantic_blocks
  for outline-aware content extraction). KeyBERT and spaCy were being fed raw
  outline-structured text that still contained literal structural labels like
  "Module N:" and "Topics:" — the NLP models correctly-but-uselessly extracted
  those labels as if they were real content/keyphrases.

FIX
  Added _flatten_outline_for_nlp() in local_ai_provider.py. This function:
    - Strips "Topics:" label lines entirely
    - Converts "Module N: Title" heading lines into a running "current_heading"
      context variable (not emitted directly as a sentence)
    - Converts each "- bullet" line into a clean sentence:
        "{current_heading}: {bullet}."
    - Passes the result through _build_study_notes() instead of raw outline text

  generate_notes() now calls:
        flattened = _flatten_outline_for_nlp(combined)
        summary_text, key_points, glossary = await asyncio.to_thread(_build_study_notes, flattened)

  The "Source material referenced" section was also changed from raw
  chunk[:280] slicing (which truncated mid-word/mid-content) to splitting the
  flattened text into sentence units.

VERIFICATION
  Direct test showed clean output: "Current Recruitment Processes",
  "Data-Driven Recruitment" instead of garbage fragments.

KNOWN REMAINING GAP (not fixed today, diagnosed only — see section 6)
  Existing/cached notes generated by the PRE-FIX code (e.g. for
  student_assessment_id=20) still contain the old garbage-derived text
  because notes are cached in Redis for 7 days (NOTES_CACHE_TTL_SECONDS) and
  there is no regeneration/cache-bust endpoint. New notes generated after
  the fix are clean; old ones are stale until cache expiry or manual purge.

4. BUG C — PDF visual design bugs ("not looking good, need colorful and
   professional")
================================================================================

4.1 Topic chip text overlap/clipping
  SYMPTOM
    Strong/Weak topic "chips" (e.g. "measuring recruitment") visually
    overlapped or clipped adjacent chip text.

  ROOT CAUSE (confirmed via isolated reportlab test script)
    _topic_chips() built each chip as its own mini-Table with a per-chip
    colWidths request (e.g. max(len(t)*5.5+12, 60)), then placed 4 chips per
    row into an OUTER Table with NO explicit colWidths. reportlab divides
    available width EVENLY across all columns of a Table when colWidths is
    omitted — confirmed directly: all 4 columns became exactly 250.0pt each
    regardless of each chip's actual requested width (127.5, 149.5, 127.5,
    89.0pt). Longer chip text got squeezed into a uniform forced-width
    column, causing visual overlap.

  FIX
    Rewrote _topic_chips() to:
      - Measure each chip's real text width via
        reportlab.pdfbase.pdfmetrics.stringWidth(text, font, size) + padding
      - Greedily pack chips into rows: add a chip to the current row only if
        the running total width + gap stays under max_w (the available
        column width); otherwise start a new row
      - Render each row as its own Table with EXPLICIT per-chip colWidths
        (the real measured widths), eliminating the even-division bug
      - Return a list of [row_table, spacer, row_table, spacer, ...]
        flowables instead of a single fixed-grid Table

4.2 Emoji glyphs rendering as black squares
  SYMPTOM
    "Strong Topics" checkmark (✔), "Weak Topics" cross (✘), and the AI
    summary lightbulb (💡) rendered as solid black squares (■) in the PDF.

  ROOT CAUSE
    Base-14 Helvetica (the only font used, no embedded Unicode font) does
    not support these Unicode glyphs / they fall outside WinAnsiEncoding.

  FIX
    Removed all three emoji characters entirely. Replaced with plain text:
      "✔  Strong Topics"  -> "Strong Topics"
      "✘  Weak Topics"    -> "Weak Topics"
      "💡  {summary}"      -> "<b>TIP:</b>  {summary}"
    (An HTML-entity checkmark/cross approach was considered and briefly
    applied, then reverted in favor of plain text since base-14 Helvetica
    cannot reliably render those code points either.)

4.3 Misleading "Score" metric denominator
  SYMPTOM
    Score metric displayed e.g. "2.0 / 17" where 17 was NOT the assessment's
    total marks — it was student_assessment.assessment_id (the database
    primary key of the related Assessment row), coincidentally similar in
    magnitude to a real total_marks value, making the error easy to miss.

  ROOT CAUSE
    Score row built as:
        f"{score:.1f} / {student_assessment.assessment_id}"
    instead of referencing the actual Assessment.total_marks field.

  FIX
    - _render_pdf() signature extended to accept a new total_marks: int
      parameter
    - generate_pdf() now fetches the related Assessment row via
      self.repo.get_assessment(student_assessment.assessment_id) and passes
      assessment.total_marks (or 0 if missing) through to _render_pdf()
    - Score row now reads: f"{score:.1f} / {total_marks}"

4.4 Dead code cleanup
    Removed an unused _chip() helper function (3 lines) left over from an
    earlier design iteration — confirmed zero call sites before removal.

VERIFICATION (all of section 4)
  Regenerated PDF for student_assessment_id=20, rendered pages to PNG via
  PyMuPDF, visually confirmed:
    - Chips wrap cleanly onto multiple rows with no overlap/clipping
    - No black-square glyphs anywhere in the document
    - Score metric correctly reads "2.0 / 10" (real total_marks) instead of
      the previous assessment-id-as-denominator value
    - Study Plan table, Trainer Remarks box, and footer all render with
      correct colors, rounded corners, and no overflow across all 10 pages

5. PRODUCTION DEPLOYMENT ISSUE — Stale uvicorn process (separate incident)
================================================================================
SYMPTOM
  After all fixes above were committed to report_service.py, the live
  Next.js app continued to show:
    POST /api/assessment/20/report 500
  even though a direct in-process test of the same code succeeded.

DIAGNOSIS
  Reproduced the failing request directly against FastAPI with a manually
  minted JWT (python-jose, using JWT_SECRET from .env) for student_id=10
  (the owner of student_assessment_id=20):
    POST http://localhost:8001/api/v1/assessment/report/20/run-now

  The returned traceback referenced report_service.py line 494 / line 423 —
  but the CURRENT file's line 494 is blank (just before the @dataclass
  ReportService declaration) and line 423 doesn't correspond to the current
  Trainer Remarks section either. This proved the running uvicorn worker
  (PID 24392) was executing STALE bytecode from before all of today's edits.

  Confirmed via process inspection: uvicorn was launched as
    python.exe ".venv\Scripts\uvicorn.exe" app.main:app --host 127.0.0.1 --port 8001
  with NO --reload flag, so it never picked up any file changes made during
  the session — it was still running the pre-fix code (broken chip grid,
  emoji glyphs, assessment_id-as-denominator, and the original
  _markdown_to_reportlab line-joining bug).

FIX
  - Killed the stale process (Stop-Process -Id 24392 -Force)
  - Confirmed port 8001 freed (no LISTENING entry)
  - Relaunched uvicorn against the current codebase:
        python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
  - Polled until /docs returned 200 (ready after ~1s)

VERIFICATION
  Re-ran the identical POST /api/v1/assessment/report/20/run-now request
  with the same JWT — received 200 OK with a valid report record:
    {"success":true,"data":{"id":7,"status":"ready",
     "file_path":"...report-20-80b32a63f476410ab5109bc548fa634f.pdf", ...}}

6. OUTSTANDING / NOT YET FIXED (flagged, not actioned today)
================================================================================
  - Stale AI notes content for older assessment attempts (e.g.
    student_assessment_id=20) still contains pre-fix garbage outline
    fragments (e.g. "Module 3: Enhan...", truncated mid-word with a literal
    "..." baked into the stored string). Root cause fully diagnosed:
      a) _extract_key_points() hard-truncates matched sentences over 220
         chars via match[:217] + "..." — truncation lands mid-word because
         the source is flattened outline text, not real prose.
      b) The "Source material referenced" section splits flattened text on
         ". " as a sentence delimiter, but flattened outline text doesn't
         reliably contain real sentence-ending periods at those boundaries,
         so the 5th slice can land mid-phrase.
    NOT FIXED YET — diagnosis only, per explicit instruction to diagnose
    before fixing. Also requires a Redis cache-bust (7-day TTL) or waiting
    out the TTL to surface any fix in already-cached notes.

  - No automatic regeneration endpoint exists for AI notes — would need to
    be added if stale cached notes need to be refreshed without waiting for
    natural TTL expiry.
