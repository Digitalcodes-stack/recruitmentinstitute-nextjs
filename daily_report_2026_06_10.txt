PROBLEM:
  The admin reviews page had no moderation capability. Reviews from students
  were being displayed with no way for admin to approve, reject, or remove them.
  The reviews table also had no status tracking.

DATABASE CHANGE (prisma/schema.prisma):
  Added a `status` column to the CourseReview model (mapped to `reviews` table):

    model CourseReview {
      ...
      status    String  @default("pending")
      ...
    }

  The column defaults to "pending" so all existing reviews are treated as
  pending moderation without needing a data migration.

CRITICAL TECHNICAL CHALLENGE — Prisma Stale Cache:
  Due to Next.js 16 Turbopack's aggressive caching, the Prisma generated client
  was serving stale compiled chunks that didn't know about the new `status` field.
  This caused: PrismaClientValidationError: Unknown field 'status'

  RESOLUTION: Bypassed the stale Prisma ORM types entirely by using raw SQL:

    await prisma.$queryRaw`SELECT r.id, r.status, COALESCE(r.status,'pending') ...`
    await prisma.$executeRaw`UPDATE reviews SET status = ${status} WHERE id = ${id}`
    await prisma.$executeRaw`DELETE FROM reviews WHERE id = ${Number(id)}`

  This is a deliberate architectural decision to work around the Turbopack
  cache issue until a full `.next` folder clean is done in production.

ANOTHER DB CHALLENGE — Column naming:
  Discovered the course_category table uses non-standard column names:
    - Primary key:  course_category_id  (not 'id')
    - Name column:  course_category     (not 'name')

  The JOIN query was fixed to:
    JOIN course_category c ON c.course_category_id = r.course_category_id

BUGS FIXED DURING THIS SESSION:

    Root cause: Regex /\b(hi|hello)\b/ requires exact word-boundary match.

    Fix: Changed to anchor-based fuzzy regex: /^(hi+|hey+|hello+|hii+|hai|...)/

  CHALLENGE 1 — Prisma Stale Cache (PrismaClientValidationError)
  ─────────────────────────────────────────────────────────────────
  Next.js 16 with Turbopack aggressively caches compiled Prisma client chunks.
  After adding the `status` field to the Prisma schema and running
  `prisma generate`, Turbopack continued serving the old compiled chunk
  that didn't know about the new field.

  ERROR: PrismaClientValidationError: Unknown field 'status' on model CourseReview

  RESOLUTION:
    Strategy: Bypass Prisma ORM types entirely for affected queries.
    Use $queryRaw (for SELECT) and $executeRaw (for INSERT/UPDATE/DELETE).
    These bypass the generated TypeScript types and go directly to PostgreSQL.
    This is a pragmatic workaround that is safe because:
    - Queries are parameterized (no SQL injection risk)
    - The raw SQL is explicit about column names (no ORM type confusion)

  LONG-TERM FIX: Delete .next folder and run clean build. This forces
  Turbopack to recompile all chunks with the latest Prisma generated client.


  CHALLENGE 2 — PostgreSQL Non-Standard Column Names
  ─────────────────────────────────────────────────────────────────
  The course_category table uses custom column names that don't follow
  standard Rails/Prisma conventions:
    - PK column: course_category_id (not 'id')
    - Name column: course_category (not 'name')

  ERROR: ERROR: column "c.id" does not exist

  RESOLUTION:
    Queried information_schema.columns to discover actual column names.
