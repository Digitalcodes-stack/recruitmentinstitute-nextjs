1.1 Razorpay Enrollment Modal — Full-Width / Unstyled Rendering
--------------------------------------------------------------
Symptom: The enrollment modal (RazorpayCheckoutModal.tsx) rendered edge-to-
edge across the full browser width, top-anchored, no border-radius, no
padding — despite the component JSX having correct Tailwind classes
(max-w-lg, rounded-3xl, p-7, flex items-center justify-center, etc.)

Investigation:
  - Ruled out: stale .next build cache (cleared repeatedly, no change)
  - Ruled out: dev server needing restart (restarted multiple times)
  - Root cause found via live Playwright screenshot + computed-style
    inspection of the actual rendered DOM:

    ROOT CAUSE #1 (globals.css line 8):
      --container-*: initial;
    This line was intended to reset Tailwind's built-in ".container"
    component scale. In Tailwind v4, --container-* is the SAME namespace
    that generates ALL max-w-* utilities (max-w-sm, max-w-lg, max-w-xl,
    max-w-6xl, etc.) sitewide. Setting it to `initial` silently deleted
    every max-w-* utility class in the entire compiled CSS bundle —
    confirmed via direct bundle inspection (grep found ZERO instances of
    max-w-lg, max-w-xl, etc. in the compiled output).
      FIX: Removed the line entirely. The project's actual container
      layout uses a separate, hand-rolled `.container { max-width: 1320px }`
      class (globals.css line ~87) that never referenced --container-* in
      the first place, so nothing was actually depending on the reset.

    ROOT CAUSE #2 (globals.css line 49-53):
      * { box-sizing: border-box; padding: 0; margin: 0; }
      This reset lived as a plain, UN-LAYERED CSS rule. In CSS cascade
      rules, ANY unlayered style always beats ANY @layer style regardless
      of selector specificity or source order. Tailwind v4 emits all its
      utility classes (p-*, m-*, space-y-*, gap handling, etc.) inside
      @layer utilities. This meant the plain `* { padding: 0; margin: 0; }`
      was silently overriding EVERY Tailwind padding/margin utility on
      EVERY page of the site, sitewide — not just the modal.
      FIX: Wrapped the reset in `@layer base { ... }` so it now loses to
      utilities the same way Tailwind's own preflight reset does.

  Files changed: src/app/globals.css

  Verification: Live Playwright screenshot before/after confirmed the
  modal now renders correctly centered, rounded, and properly spaced.
  This was a genuine SITEWIDE bug affecting every page using max-w-* or
  spacing utilities — not limited to the one modal reported.

1.5 Admin "Edit Trainer" Page — Availability Not Displayed After Save
-----------------------------------------------------------------
Symptom (reported by user with screenshot): user set a trainer's weekly
availability to Sat 06:00-23:00 (custom hours) plus other days, saved it,
then reopened the Edit Trainer page and only saw Sunday selected — appeared
as if the save had failed or been overwritten.

Investigation: Queried the database directly for that trainer's saved
TrainerAvailability rows. CONFIRMED all 7 days were correctly persisted,
including the exact custom Saturday 06:00-23:00 time. The data was never
lost — the bug was purely in what the edit page displayed.

Root cause: src/app/(admin)/admin/trainers/[id]/edit/page.tsx ran a Prisma
`select` for the trainer record that did NOT include the `availability`
relation at all. TrainerForm.tsx therefore always received `availability:
undefined` on every page load, regardless of what was actually saved,
and always rendered as if the trainer had zero availability configured.
Any subsequent save from that state would have genuinely overwritten the
real data with whatever was visible in the (incomplete) form.

Fix: Added `availability: { select: { id, dayOfWeek, startTime, endTime } }`
to the Prisma select in the edit page query.

Files changed: src/app/(admin)/admin/trainers/[id]/edit/page.tsx

Verification: Re-ran the exact corrected query directly against the DB —
confirmed it now returns all 7 previously-saved availability rows for the
affected trainer (Brahmita Nayak, trainer id 7).

2.1 Trainer Availability System (CRITICAL requirement)
-----------------------------------------------------------------
Schema (prisma/schema.prisma):
  New model `TrainerAvailability`:
    - trainerId (FK to Trainer, cascade delete)
    - dayOfWeek: Int (0=Sunday .. 6=Saturday, matches JS Date#getDay())
    - startTime / endTime: String, "HH:mm" 24-hour, IST wall-clock
    - One row per recurring weekly slot; a trainer can have multiple rows
      per day (multiple time windows) and any number of days
  Added `timezone: String @default("Asia/Kolkata")` to the Trainer model.
  Pushed to the live database via `prisma db push` (NOT `prisma migrate
  dev` — this project has no existing migration history, so `migrate dev`
  would have demanded a full destructive database reset; db push updates
  schema in place with zero data loss).

Admin UI (components/admin/TrainerForm.tsx):
  - Day-of-week pill selector (Sun-Sat, multi-select)
  - Per-day time-range row(s): start time / end time pickers
  - "+" button to add multiple time slots on the same day
  - "x" button to remove a slot
  - Validation: end time must be after start time for every slot
  - Helper copy: "Times are IST. Used to auto-assign trainers to new
    batches."

API (src/app/api/admin/trainers/route.ts and [id]/route.ts):
  - POST (create): accepts `availability: [{dayOfWeek, startTime, endTime}]`,
    creates trainer + availability rows in one call
  - PUT (update): availability has no stable per-slot ID from the client,
    so update is implemented as delete-all-then-recreate inside a Prisma
    transaction (safe, atomic, correct for a small list of ~7 rows)
  - GET: both list and single-trainer endpoints now select and return
    availability

Public trainers page: now shows real trainers with real availability data
(see 1.3 above for the page-level fix that made this visible at all).

2.2 Automatic Next-Batch Generation + Smart Trainer Assignment (CRITICAL)
-----------------------------------------------------------------
lib/services/trainerAvailability.ts (NEW FILE):
  `findAvailableTrainers(requirement, opts)`:
    - Takes { classDays: number[], startTime, endTime } + optional
      specialization hint
    - Returns only ACTIVE trainers whose declared availability rows fully
      COVER every requested class day and time window (a trainer's slot
      must span the entire requested window, not just overlap it)
    - A trainer with ZERO availability rows is always excluded — never
      guessed into an assignment
    - Ranks candidates by: (1) fewest currently active/upcoming batches
      first [load-balancing], (2) specialization text match as tiebreak
  `pickBestTrainer(requirement, opts)`: returns the top-ranked candidate
  or null.

lib/services/nextBatchGenerator.ts (NEW FILE):
  `generateNextBatch(courseId, options)`:
    - Looks up the course's most recent batch (by start date); if none
      exists, uses today as the baseline
    - Computes the earliest valid next start date as
      max(lastBatch.end/start + gapDays[default 14], today), then advances
      to the next date matching the requested class days
    - Calls pickBestTrainer() for the requested schedule; throws a typed
      `NoTrainerAvailableError` (with a human-readable message naming the
      exact days/times that had no coverage) if nobody qualifies —- this
      is surfaced to the admin UI as a clear message, not a crash
    - Creates the Batch record (auto-generated name: "{Course title} —
      Batch N"), then calls the EXISTING `generateSessionsForBatch()`
      service (already in the codebase, unmodified) to auto-create one
      session per syllabus module with real dates/topics and trigger the
      existing student-notification emails — deliberately reused rather
      than reimplemented
    - Returns batchId, assigned trainer, computed start date, sessions
      created, and the full session preview

API: POST /api/admin/courses/[id]/generate-next-batch
  - Admin-auth guarded
  - Accepts optional override body: classDays, startTime, endTime,
    capacity, mode, gapDays
  - Returns 201 with the generation result, or 409 with code
    NO_TRAINER_AVAILABLE and a descriptive message if no trainer qualifies

Admin UI: "Generate Next Batch" button added to CourseActions.tsx (the
per-course action row on Admin > Courses). Calls the API, shows the result
in an alert (batch name, trainer assigned, sessions created, start date),
then navigates to the new batch's detail page.

LIVE FUNCTIONAL TEST PERFORMED (not just code review):

2.3 Certificate Issuance (business feature #3 — PARTIAL)
-----------------------------------------------------------------
Schema: New `Certificate` model — one per Enrollment (unique), stores
certificate number, student name + course title SNAPSHOT (so later name/
title changes don't retroactively alter an issued certificate), final
score, issue date, optional PDF URL.

Service (lib/services/certificates.ts):
  `issueCertificate(enrollmentId, finalScore)`:
    - Idempotent: throws AlreadyCertifiedError if one already exists for
      that enrollment (never silently duplicates)
    - Enforces a passing-score threshold (flat 50%, marked with a
      "ponytail:" code comment flagging this as a placeholder to make
      configurable per-course later if the business needs differ)
    - Generates certificate number as RI-CERT-{year}-{enrollmentId
      zero-padded to 6 digits}
    - Sends a confirmation email via new sendCertificateIssuedEmail()
      function in lib/email.ts (matches existing email style/branding)

API: POST /api/admin/enrollments/[id]/certificate — admin-triggered,
  accepts { finalScore } in the request body.

EXPLICITLY NOT DONE (flagged, not silently skipped): automatic issuance
triggered by a student passing their final assessment. Investigated the
grading pipeline and confirmed assessment scoring lives entirely in the
separate FastAPI backend service (via SessionAssessment.fastapiAssessmentId
foreign pointer + lib/fastapiClient.ts), not in this Prisma database. No
verified webhook or callback contract exists yet between that service and
this one, so building an automatic trigger would have meant guessing at
an unconfirmed integration point. Built the safe manual-trigger path
instead and left the automatic wiring as an open item pending that
contract being defined.

Also not done: actual PDF certificate generation/rendering — no PDF
library exists in the project yet (would need e.g. pdf-lib added when
this becomes a real requirement).

2.4 Batch-Start Countdown Reminders (business feature #6)
-----------------------------------------------------------------
This is distinct from the SESSION-level reminders that already existed
in the codebase (lib/jobs/sendReminder.ts, 24h/1h/15m before an individual
live class). This new feature reminds people about an entire BATCH
starting soon.

lib/jobs/sendBatchStartReminder.ts (NEW FILE):
  `sendBatchStartReminder({batchId, lead: '3d'|'1d'})`:
    - Emails every actively-enrolled student in the batch AND the
      assigned trainer
    - Skips CANCELLED batches
  `scheduleBatchStartReminders()`:
    - Scans for UPCOMING batches whose start date falls in the
      "exactly 3 days from now" or "exactly 1 day from now" windows
    - For each match, enqueues one job into the EXISTING JobQueue table
      (type: 'send_batch_start_reminder') — reused the project's existing
      generic pending/runAfter/attempts/backoff job queue rather than
      building a new mechanism
    - De-duplicates: will not re-enqueue if a job for that exact
      (batchId, lead) pair already exists in pending/processing/completed
      state — but WILL retry if a prior attempt failed, since failed jobs
      are excluded from the de-dupe check (this was a deliberate fix
      during implementation — an earlier version would have permanently
      blocked retries after any single failure)

Email template: new sendBatchStartReminderEmail() in lib/email.ts,
role-aware copy (different wording for student vs trainer recipient).

Wiring: src/app/api/internal/cron/tick/route.ts — the project's existing
Vercel cron endpoint (already configured to fire every 5 minutes via
vercel.json) now also calls scheduleBatchStartReminders() on every tick,
and the new job type is registered in the existing HANDLERS dispatch map.

IMPORTANT CAVEAT (explained to user): Vercel's scheduled cron only
executes in a deployed environment. On localhost, nothing calls
POST /api/internal/cron/tick automatically — it must be invoked manually
(with the CRON_SECRET bearer token) for the reminder scan to actually run
during local testing.

Files added: lib/jobs/sendBatchStartReminder.ts
Files changed: lib/email.ts, src/app/api/internal/cron/tick/route.ts
